# Справочник по экспортёру: где что искать

Часть инструкции `AGENTS.md` (таблица-развилка — в разделе «Что читать когда»).
Читай подраздел, соответствующий просьбе владельца, а не весь файл.
Номера строк не указаны (они плавают) — ищи по **именам функций и ключевым английским словам комментариев** через `grep`.
Файл `export/mcworldexporter.cpp` целиком не читай. Метро, вокзалы и рельсы — в отдельном файле `.agents/metro.md`.

### Как сшиваются здания из нескольких частей (building:part, комплексы, башня на подиуме, висящие части)
Цепочка из трёх этапов, каждый в своём месте:
1. **Чтение и привязка частей — `input/tmcproject.cpp`, блок с комментарием `BUILDING PARTS (building:part)`.** Правила кладут часть в слой `bldpol` с `PART=1`. Дальше: каждая часть привязывается к «хозяину» (контуру здания) по пересечению площади (≥30% части); контур хозяина уменьшается на объединение частей (`Difference`); если от контура почти ничего не осталось — удаляется. Часть наследует код (`CODE`), материал (`MAT`) и адрес хозяина; адрес получает только самая большая часть. Метка `PART` после блока становится `part` (нужна экспортёру: мелкие части получают тонкие стены).
2. **Поднятые части (`min_height` / `building:min_level`) — тот же файл + `osm_rules.json` (правила «raised above the ground») + `scene/mcscene.cpp`.** В `addObjects` считается `MINH` (высота основания в метрах; по этажам — этаж из `height/levels` или 3.3 м). Блок «Raised parts (MINH, meters)» после блока частей превращает `REL` (высота верха) в толщину части: `REL = max(3, верх − MINH)`. `default.t3d` поднимает основание по полю `MINH` (`liftField`), `mcscene.cpp` ставит `McObject::raised` (метры).
3. **Склейка и построение — `export/mcworldexporter.cpp`:**
   - `raiseLowBuildingParts` — низкие части подтягиваются до ≥7.6 блока;
   - в `Export()` после него — вычисление `thin` для мелких частей (стены в 1 блок: флаг `thinW` в `voxelizeObject`);
   - **`mergeIndustrial`** — главная сшивка: касающиеся или перекрывающиеся здания **одного кода** склеиваются в один объект (`merged=true`, объединённый меш). Кандидаты: `mergeableCode()` (промзона 44340000, церковь 44319000, нежилые 44310000…44318000), любые поднятые части, а жилые 44400000 — только если над ними висит поднятая часть и планы пересекаются. Лимиты: габарит ≤140 блоков, ≤60 частей. У склейки поле `raised` = минимум по частям, `floatCols` = колонки, над которыми только висящие части (земля под ними не поднимается);
   - в **`voxelizeObject`**, блок `if (obj.merged)`: внутренние стены между телами (по осям X и Z) и **перекрытия между телами друг над другом (ось Y)** удаляются — внутреннее пространство общее; этажи и лестницы кладёт обычный проход по всему «столбу»;
   - отдельный объект с `raised>0` (не склеенный) строится «парящим» (`raisedObj`: без фундамента, входа, подвала, без записи в `colMin`);
   - проходы после `flushJobs()`: **нижний ряд стен висящей части из светло-серого бетона** (комментарий `The bottom row of the walls of a raised part`), **стремянка в висящую часть** (`Access to the raised building parts`: шахта через плиту + лестница, только внутри здания), купола, односкатные крыши.
4. Склейки лифтовых шахт (`LIFT=1`) устроены отдельно: `liftJobs` — шахта строится после всех зданий и только выше крыши своего здания.

### Как устроены правила экспорта: OSM-теги → слои → коды (`osm_rules.json`)
- Файл `resources/osm_rules.json`, читает `osm/tmcosmrules.cpp` (`TmcOsmRules::classify(from, tags, pass)`), применяет `input/tmcproject.cpp` (функция `addObjects` и окружающий цикл по слоям GDAL `points`/`lines`/`multipolygons`).
- Правило: `from` (слой драйвера OSM), `when` (условия по тегам: значение, `"*"` тег есть, `"-"` тега нет, `"!v"`, списки, `"~re"` регулярка, числа `">=4"`, служебные `_area`, `_perim`, `poi:<тег>`, `area:<тег>`, `nb:*` для второго прохода), `layer` (`bldpol`, `vegpol`, `vgbpol`, `csrpol`, `hdrpol`, `hdrlin`, `rdslin`, `rrslin`, `rdcpol`, `blkpol`, `csrlin` — линейные объекты культуры (CODE 82200000 — забор из `barrier=fence`), `csrpnt`/`hdtpnt` — точечные объекты, `mrspol` — болота, `-` = не брать), `fields` (шаблоны `{тег}`, `{тег1,тег2}`, `||` — запасной вариант), `as` (`polygon`, `line`, `crosswalk:N`, `square:N` — преобразование геометрии). Срабатывает **первое** подходящее правило сверху, если нет `"continue": true`. Подробное описание — раздел `_help` в начале файла.
- **Коды `CODE`** — это тип объекта (список — `resources/heights.csv`): 44000000 сарай; 44310000 нежилое; 44311000 администрация; 44312000 школа; 44313000 детсад; 44314000 больница; 44315000 НИИ; 44316000 культура; 44317000 музей; 44318000 торговый центр; 44319000 церковь; 44340000 промзона; 44400000 многоквартирный дом; 44400002/44400100/44400110 частный сектор, дачи, коттеджи (скатная крыша); 31xxxxxx вода; 45xxxxxx/61xxxxxx дороги; 71xxxxxx растительность. Код определяет облик в `export/mcworldexporter.cpp` (ищи `obj.code ==`).
- **Высота `REL`**: `"REL": "auto"` → `osm/tmcrel.cpp: tmcAutoRel` (тег `height` → `building:levels` по формулам этажей → типовая по коду из `heights.csv` → 6 м). **Материал `MAT`** — из `building:material` / `building:facade:material`; в экспортёре — `materialBlockId()`.
- **Два прохода**: правила с `"pass": 2` видят только то, что не опознал первый проход.
- Служебные поля, которые добавляет `tmcproject.cpp` поверх правил: `MINH` (высота основания), `PART`, `ROOF` (`onion`/`skillion`), `ROOFH` (`roof:height`), `ROOFD` (`roof:direction`), `ROOFC`/`ROOFM` (`roof:colour`/`roof:material` купола), `TYSTR`/`STREET`/`NUMBR` (адрес, `osm/tmcaddress.cpp`).
- Чтобы новое поле дошло до блоков: правило/`tmcproject.cpp` → имя поля в `L->fieldNames` → чтение в `scene/mcscene.cpp` (`ExportItem` → `McObject`) → использование в `mcworldexporter.cpp`.
- Если нужно, чтобы не было правила под тег — проверка `--dry-run` и переменная `TMC_OSM_UNMATCHED=файл.tsv` покажут необработанные объекты.

### Как здание превращается в блоки (`voxelizeObject`)
Функция `voxelizeObject` (в `mcworldexporter.cpp`) вокселизует один объект: растеризует треугольники меша в сетку (`grid`: 0 воздух, 1 поверхность, 2 внешний воздух, 3 тело, 4 внутренняя обшивка, 5 лестница/шаг), заливает внутренность «flood fill» снаружи, делает полость с оболочкой в 2 блока. Дальше по порядку (ищи по комментариям): стены (`structFor` — фундамент, 2 нижних и 2 верхних ряда из `structId`), окна (**`windowDir`** — профили: жилые 1×2/2×2, нежилые 2×3 `bigWin`, торговые центры панорама `panor`, материал «стекло» панорама `panoWin`; в двух верхних рядах колонки окон нет), входы (`BUILDING ENTRANCES`), этажи и перекрытия (`Inter-floor slabs`), лестницы между этажами (`Inter-floor stairs`, при нехватке места — стремянка), перегородки (`partitions`), мебель и интерьеры (`"Interiors" v2`), сундуки/спавнеры/жители, подвалы (`BasementSite`), крыши частного сектора из ступеней.
- Объекты строятся параллельно (`VoxJob`, `flushJobs`), результаты сливаются **в порядке объектов**: более поздний объект перекрывает ранний.
- `decorateWalls` — цветные полосы детсадов (без жёлтого/оранжевого), белые вертикали школ, красные пояса НИИ.
- Фундамент: `sink` (2 блока в землю; частный сектор и сараи — 1), рост по высоте `extraBlocks`. Здание помечает колонки в `colMin`/`colAnchor` — по ним земля под зданием поднимается/выравнивается.
- **Окна на «ступеньках» повёрнутых частных домов** (заказ «окна могут быть на ступеньках, реальные окна, а не блестящий фасад; на реальных углах — нет»): в `buildGrid()` по проекции контура строится выпуклая оболочка (Andrew, монотонная цепь) — её вершины это РЕАЛЬНЫЕ углы дома, колонки вокруг них кладутся в `cornerCols` (по 2×2 у каждой вершины). В `windowDir()` ветка `xw == zw` (две открытые грани = ступенька лесенки повёрнутой стены) больше не глухая для `priv`: если колонка не в `cornerCols` — окно разрешается; направление выбирается `runTo()` — по оси, которая через МИНИМУМ клеток стены доходит до внутреннего воздуха (char 3), иначе до внешнего (тонкий зуб). `buildWalls()` для ступеньки идёт по нормали и кладёт стекло во ВСЕ клетки стены (char 1/4) до внутреннего/внешнего воздуха (до 4 клеток), помечая их 5 — окно получается насквозь через всю толщу (раньше второе стекло ставилось только в обшивку char 4 — в диагональной стене за стеклом оставалась кирпичная кладка: «блестящий фасад»). Обычные окна и горшки не тронуты. ⚠️ Прежнее правило `xw == zw → 0` глушило ВСЕ клетки диагональной стены 45° (каждая имеет две открытые грани) — у такого дома было ноль окон.
- **Доворот частных домов к осям** (заказ «лесенка стен и нет окон»): проход перед диспетчером объектов, счётчик лога «houses straightened to the axes». Замкнутый объект частного кода (44400002/44400100/44400110) с bbox ≤60×60 блоков доворачивается к БЛИЖАЙШЕЙ оси В БЛОКОВЫХ координатах вокруг центроида (высоты не трогать; центроид стоит — «центровые» consumers не съезжают); не трогаются только уже почти осевые (<1°). Формула angles: `ang` из `atan2` нормализуется в [0,180), угол доворота `rot = 90*round(ang/90) - ang` (короткий, |rot|≤45). ⚠️ ЛОВУШКИ (все три проверены на заказе): (1) прежняя ветка `ang>45 ? ang-90 : -ang` давала НЕВЕРНЫЙ ЗНАК — дома >45° доворачивались ОТ оси; (2) угол брался как «самое длинное ребро» по СОСЕДНИМ вершинам меша — а вершины меша не упорядочены по контуру, ребро получалось произвольным; теперь берётся самое длинное ребро ВЫПУКЛОЙ ОБОЛОЧКИ контура (Andrew); (3) `rot` в ГРАДУСАХ передавался в `std::cos/std::sin` без `* kPi/180` — дом доворачивался на cos(градусы) = случайный угол; владелец видел «слабо доворачиваются». Делать так и для других кодов — только по просьбе: у многоэтажек доворот снёс бы сетку колонн. Доворот НЕ применяется, если повёрнутый контур налегает на строения ДРУГИХ типов (кроме сараев 44000000) — заказ владельца: частные дома могут сливаться друг с другом и залезать на сараи, но не на чужие здания; тогда дом остаётся в ориентации OSM. Соседние «чужие» здания находятся по bbox (расширение под качание углов при повороте), их footprints растеризуются параллельно один раз в `foreignCols`; допускается касание ≤2 колонок (общая стена OSM), больше — дом не доворачивается. Счётчик лога: «houses straightened to the axes: N (kept off other buildings: M)».

### Как строятся крыши (купола, односкатные, скатные)
- Плоская крыша — верхние 2 ряда оболочки. Частный сектор (44400002/44400100/44400110) — двускатная крыша из ступеней (внутри `voxelizeObject`).
- **Купола** `roof:shape=onion|dome` и **односкатные** `skillion` — проходы после `flushJobs()` в `Export()`: комментарии `Domes of churches` и `Monopitch roofs`. Купол: цвет по `roof:colour`/`roof:material` (ближайший бетон; **белый — полированный кварц `smooth_quartz`, не бетон**; без цвета и известного материала — **простой серый бетон**, без шпиля; шпиль только у жёлтого/золотого, синего, голубого, красного, чёрного — золото/лазурит/алмаз/редстоун/уголь; стекло — полусфера, потолок под ней вырезается). Односкатная: клин от нижнего края к верхнему по `roof:direction`, высота `roof:height`. Тело под такой крышей ниже на `roof:height` (правка `REL` в `tmcproject.cpp`).
- Новые формы крыш добавляй так же: поле из тегов в `tmcproject.cpp` → `McObject` → отдельный проход в `Export()` по готовому `store`.

### Земля, вода, дороги, мосты, железные дороги
- Земля (`step 3`, комментарий `3. Ground`): колонки всех затронутых чанков; `groundTopCol(x,z)` — уровень поверхности; `colMin` поднимает землю под зданиями (не выше +3 блоков над естественным уровнем), `colWater` — карта «колонка → глубина водоёма», `colWool` — площадки `csrpol`/покрытия (бетон/шерсть вместо дёрна), `roadCols` — дороги, `paleCol` — лес скрипунов, `makeGround` — сборка `GroundChunk` (верх, поверхностный блок, вода).
- Дороги `rdslin`: ленты → ковёр/бетон с разметкой и зеброй; `roadsHigh`/`roadsLow`, `paintBody`, `roadCols`. Железные дороги `rrslin` — рельсы по оси (`railCellChain`, `railShapeFor`). Метро (61123100): перед `railCellChain` полилиния **спрямляется** в диспетчере (реальные линии — длинные диагонали, сетка превращает их в лесенку с поворотом на каждом блоке): каждый диагональный участок идёт 10 блоков ПРЯМО, потом 20 блоков ДИАГОНАЛЬЮ back toward the real mapped line (`rc=min(1, 1.5·dc/da)` — возврат meets the true line ровно в узле); при отклонении ≤1 блока участок просто повторяет исходную OSM-полилинию до узла; узлы (станции/перегибы) остаются на месте. ЗОННЫХ guard'ов больше нет — линии можно поворачивать где угодно. Проход тоннеля строит оболочку **двумя фазами**: сначала union-карты по ВСЕМ цепям (`tInt` — колонки интерьера, глубокий пол+`maxFloor`+`minU`; `tWallLo/Hi` — ряды стенки [min..max]), затем запись: интерьер всегда побеждает стенку (иначе стенка соседнего пути стояла в чужом коридоре «колонной»), пол — самый глубокий, скругление `minU==2` только там, где ничей более широкий интерьер. Колонка, занятая цепями с разными этажами, не затирается чужим «восстановленным камнем»: интерьеры этажей прорезаются раздельно, при разнице этажей ≥5 между ними — плита пола верхнего этажа (иначе верхний коридор запечатывался породой нижнего — «колонны» на реальных пересечениях двух путей). Угловая клетка цепи заявляет СЕЧЕНИЯ по обеим осям (входа и выхода) — сечение только по оси выхода оставляло 3 колонки породы за поворотом внутри коридора (те же «колонны» на каждом изгибе). Уступ уровня не ставится на поворот (`railShapeFor` даёт уклон только на прямых; угол принудительно плоский, несколько раундов клампа). Оболочка пишется до ВСЕХ рельсов всех цепей; рельс нависает над чужим более глубоким коридором — под него подпора из `floorId`.
- Электрификация рельсов: `electrifyRails` (хелпер рядом с `railShapeFor`) — каждый 20-й рельс становится `powered_rail`, но ТОЛЬКО на прямой цепочки; «попадание» на поворот переносится дальше и ставится подряд (2–5 штук). ПОД КАЖДЫМ `powered_rail` кладётся `redstone_block` (заказ: «чтобы электрофицированные рельсы были всегда активны») — рельс на редстоуне не переходит в тормозящее состояние; редстоун пишет тот же `electrifyRails` сразу после смены рельса (все три места вызова накрыты). ⚠️ ЛОВУШКА: редстоун ПОД рельсом НЕ активирует его в экспортированном мире — чанки из anvil не получают block update при загрузке, рельс зависал с `powered=false` («не активны, хотя на редстоуне»). Свойство состояния пишет сама палитра: `blockProperties` для `IdPoweredRailShapeBase..` отдаёт `powered=true` (состояние всегда честно: под рельсом редстоун). Общее правило для новых «загорающихся» блоков: состояние активности надо писать в палитру, тика/обновления не будет. Срабатывает для метро (проход тоннеля), наземных путей с полем `ELEC`≠no (колонка `ELEC` из `osm_rules.json` → `McObject::railElec` через `mcscene.cpp`) и трамваев 61124000 (всегда). Балласт: `railBedCols` (колонка → блок) заполняется в диспетчере рельсов, `makeGround` кладёт его в поверхностный блок вместо дёрна (камень под электрофицированными, каменные кирпичи под трамваями; дорога/вода не перекрываются).
- Мосты через воду — комментарий `BRIDGES` после `lap("g4 ground fill")`: настил, балка из каменного кирпича, опоры каждые 12 блоков.
- **Эстакады и тоннели автодорог** (`bridge=yes`/`tunnel=yes`/`level=X`; колонки BRG/TUN/LVL/LYR в `osm_rules.json` → `McObject::roadBridge/roadTunnel/roadLevel/roadLayer` в `mcscene.cpp`; высота `elevH = min(40, 8·qBound(1,|LVL|,4) × (мост: qBound(1,|LYR|,4)))` — `LYR`=`{layer}` добавлен в 17 правил rdslin, у мостов layer МНОЖИТЕЛЬ высоты (заказ LA: эстакада в 2 уровня над 1-уровневой), у тоннелей игнорируется). Диспетчер только ОТМЕЧАЕТ способ: обе линии поднимаются/опускаются на ВСЕЙ длине (`off = ±elevH`), геометрией владеет проход `VIADUCTS AND TUNNELS` после `lap("g4 ground fill")`. Мост elevated если есть линия ≥7 блоков (короткие линии развязки поднимаются когда ОБА конца стыкуются, Чебышёв ≤2). Тоннель elevated если часть ≥11 блоков ИЛИ её конец ПРОДОЛЖАЕТ чужой тоннель: `EndPt` препрохода `elevatedEnds` (`{объект, bridge?, точка, outward, len}`) — cheb ≤2, направления антипараллельны (dot < −0.35), партнёр впереди а не сбоку (`fwd ≥ 0 && lat−fwd ≤ 1`), партнёр ≥11. БЕЗ проверки выравнивания встречные tubes дубли (разделённые проезжие части) стыковались «под землёй» и въезды в тоннели исчезали вовсе (ловушка 8). bridge важнее tunnel. ### Объекты из точек (`modelField` source'а) и биомы (`effect` source'а)
- Ни имён слоёв, ни хардкода в коде: роль слоя задаёт **сам source в 3D-настройках**. `VectorSource::modelField` (имя колонки с кодом объекта, у точек — «CODE») → `McObject::Spot` (Kind=9); `ModelEffect::Swamp` (бит 128) на source → `McObject::Biome` (Kind=10). В `default.t3d` так объявлены `csrpnt`/`hdtpnt` (modelField «CODE», isGround) и `mrspol` (effect 128, isGround, болота `natural=wetland`). Старые чужие `.t3d`/`.tmc` этих слоёв не содержат — и новых объектов у них нет (осознанно: всё через настройки, без хардкода).
- Правила точек используют `as: square:N` (квадрат N метров вокруг узла, центр — сама точка). CODE правила не несут REL/высот — source «на земле».
- Модель структуры: `mcscene.cpp` читает колонку `modelField` у каждого feature и ищет её код в таблице `resources/point_models.csv` (`код;модель`, рядом с exe, грузится `loadSpotModels` по образцу `heights.csv`); кода нет в таблице — объект пропускается с предупреждением (счётчиком). Номер модели доходит до экспортёра как `McObject::model`.
- Квадрат — только якорь: в диспетчере объектов ветка `o.kind == McObject::Spot` берёт растеризованные колонки (`pre`), центр bbox — якорь (`spots`), а колонки bbox+3 помечает в `noTreePadCols` — деревья не лезут на объект (проверка и в лесном цикле, и у одиночных деревьев).
- Строит шаг **3.575** (после уличной мебели 3.57, до 3.59), `switch (sp.model)` по константам `SpotModel`: 1 (`kStatue`) мемориал — 6 вариантов по хешу колонки, 2 (`kStele`) стела — 3 варианта, 3 (`kFountain`) фонтан (каменное кольцо, бассейн, столб; на столбе источник IdWater, стекающая вода по 4 сторонам — `IdWaterFalling` = water level=8 через `blockProperties`), 4 (`kTower`) вышка (основание iron_block, шпиль IdCobbleWall, 3 кварца), 5 (`kComposter`) компостер. Основание `surfaceTop+1`; под якорем вода/проезд/структура → пропуск. Исключение — вышка: на здании (`colMin`) она растёт от крыши (скан колонки сверху вниз до первого плотного не-растительного блока), при высоте здания ≥32 блок — тело 6 блоков + 3 кварца, иначе тело домножается до ~32 от земли.
- Биом-оверлей: ветка `o.kind == McObject::Biome` в диспетчере только собирает растеризованные колонки в `swampCols` (никаких якорей/падов, polygon не строится). Дальше два места: в лесном цикле шаг 3.5 ветка `swampCols.contains(ck)` (СТОИТ после pale-ветки, до park/intra/spruce) — любой лес под болотом становится рощей болотных дубов (~50% сетки); и отдельный проход перед `lap("before 3.51")` — голые болота редкими дубами (~40% ячеек сетки 6×6) и флорой (dead_bush/fern/коричневые и красные грибы, ~7% колонок); оба места пропускают `colWater`/`roadCols`/`colMin`/`noTreePadCols` и занятые колонки. Болотный дуб — лямбда `plantSwampOak` (дуб с плоской кроной); лозы — `jungleCrownVines`/`vineColumn` с параметром `leafId` (по умолчанию jungle).

### Заборы из линий OSM (csrlin, CODE 82200000)
- Заказ «заборы из линий osm с тегом barrier=fence, стыкованные между собой». Правило в `osm_rules.json` (`from: lines`, `barrier=fence` → `layer: csrlin`, `CODE 82200000`) — НЕ хардкод: экспортёр смотрит только на CODE, неизвестные коды csrlin молча пропускаются.
- `mcscene.cpp`: суффикс слоя `csrlin` → `Kind::CSRLine` (==11 в `mcworldexporter.h`); ось берётся из геометрии OGR (`ModelBuilder::ExtractLinePaths`, меш не нужен) в `McObject::paths`.
- Диспетчер объектов: ветка `o.kind == McObject::CSRLine` переводит paths в блок-координаты и растеризует `railCellChain` (цепка боковых соседей, «лесенка» для диагоналей) в множество `fenceLineCols`.
- Строит шаг **3.577** `buildFenceLines()` (после точек 3.575, ДО 3.59/3.58): на каждой колонке ДВУХЭТАЖНАЯ каменная ограда — `IdStoneFence` (`stone_brick_wall`) на `surfaceTop(ck)+1` и `+2` (заказ владельца: сначала был деревянный `IdFence`, заменён; второй этаж только когда обе ячейки `IdAir`). Пропуски: `colMin`/`colWater`/`railColsAll`, поверхностная вода (`wd>0`), занятая пара ячеек.
- **Забор важнее дороги** (заказ): динамическая ширина дорог в `rebuild()` (шаг 3.51, roadsHigh/Low/Earth) останавливает расползание ленты от осевой на ячейке забора — лямбда `fenceBlocks(ck)`; ЯДРО широкой ленты на ячейке забора тоже снимается. ИСКЛЮЧЕНИЕ — пересечение: если линия забора идёт ПОПЁК ленты (оба соседа вдоль поперечной оси тоже забор, т.е. осевая дороги пересекла забор) — ширина НЕ режется, там рвётся сам забор. После trimming `roadCols ∩ fenceLineCols` = только пересечения, и 3.577 их пропускает. Уличные и парковые фонари (`buildStreetFurniture`) тоже пропускают `fenceLineCols` (мебель не встаёт в линию забора).
- **Стыковка** — не отдельным кодом, а следующим шагом 3.58 `connectFences()`: он штампует биты connections из записанного store (впитывают соседние заборы любого происхождения, калитки и полные блоки стен), поэтому касающиеся way'и, заборы площадок csrpol и стены домов срастаются в один забор. Разные y не соединяются (ванильное поведение). В 3.58b верхняя стена делает нижнему этажу бит 16 → стороны `"tall"` + `upside_down=true` (так игра сама описывает стену на стене; `IdStoneFenceMax` = Base+32), у одиночных парконовых стен бита нет.
- `resources/default.t3d`: source `csrlin` (isGround, effect 0) — в ЧУЖИХ старых `.t3d`/`.tmc` его нет, там заборов не будет (судьба `csrpnt`). `heights.csv` не нужен (REL не читается). `app/mappreview.cpp`: цвет #8a5a2e + порядок отрисовки.
- Тест: `gen_osm_test.py` генерирует ДВА касающихся barrier=fence way (L-образный забор в пустом поле x≈758, y≈-33; `expected.json` ждёт `csrlin: {82200000: 2}`); в `.osm` вручную ничего не добавлять — он перегенерируется.

### Порядок работы экспорта (конвейер целиком; после рефакторинга — `export/exportrun.cpp`, класс `ExportRun`; `mcworldexporter.cpp` — тонкая обёртка)

### Граница полигона (`--clip`): какие чанки вообще обрабатываются
- Полигон режет мир в ДВУХ местах. Финальное слово — `assembleChunks()` (шаг 4): пишет только чанки, попавшие в `writeChunks` (пересечение с полигоном + целые здания/мелкие озёра на границе + кольцо соседей). Но тяжёлые этапы 3.x теперь ОБРЕЗАЮТ множество заливки заранее: `clipFillToBoundary()` в `buildGround()` (после блока forest-extension) оставляет в `fillChunks` только чанки, пересекающие полигон, + чанки целых зданий/мелких озёр на границе (те же правила «остаётся целым», что у `assembleChunks`) + кольцо из 8 соседей вокруг каждого оставленного чанка (∩ множество заливки). Без этого `ground` и все посадки строили землю для ВСЕГО прямоугольника шума (миллионы чанков → часы и десятки ГБ RAM).
- Множество ДО обрезки сохраняется в `fillAllChunks` — проверки крон деревьев (`plantTree`, парки, болота) читают его, а не `fillChunks`: дерево у самой границы высовывает крону в «отрезанный» чанк ровно как раньше (эта часть просто не попадёт в архив). Строительные площадки/посадки перебирают уже обрезанный `fillChunks`.
- `clipPath` (QPainterPath полигона) строится в `clipFillToBoundary()` и перезаиспользуется `assembleChunks` (тот обнуляет его перед `addPolygon`, иначе EvenOdd сложит полигон дважды).
- Счётчик лога «polygon boundary: N of M chunks written»: `M` берётся из `fillAllChunks` (до-обрезочное число), чтобы строка не изменилась по смыслу.
