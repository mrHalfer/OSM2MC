# Типичные ловушки (уже наступали)

Часть инструкции `AGENTS.md`. Читай перед тем как считать любую правку
законченной, и когда что-то непонятно не работает / строится камнем / молча пропускается.

- `VoxelStore::set(..., IdAir)` — пустая операция. Нужен `erase()`.
- Файлы из `resources/` копируются рядом с exe при сборке: забыл пересобрать/скопировать — тестируешь старые правила. Исключение — шаблоны `templates/*.bin`: они в подпапке `assets\` рядом с exe.
- `osmc.exe` заблокирован запущенной копией — линковка падает с `LNK1104`.
- Переменные окружения `PROJ_LIB`/`GDAL_DATA` чужих программ ломали проекцию — программа теперь всегда берёт данные рядом с exe (`app/main.cpp`), не меняй это.
- Тесты запускают `osmc.exe --lang en`: сообщения, которые они ищут, английские. Не меняй английские тексты логов без нужды.
- Цвета декора (детсады, школы) подобраны так, чтобы не совпадать с цветами, используемыми проверками в `tests/tools/verify_mc_export.py`. Новые цвета проверь тестами.
- Скриншоты и `images/screen/` — не в Git (кроме `images/shots` и `online_*/data_*`).
- Сети нет в тестах: не добавляй в тесты обращения к интернету.
- Сборка в **чистую** shadow-папку (`OSMC_BUILD` в несуществующий каталог) падает сразу на rcc: `RCC: Error in 'release\qmake_qmake_qm_files.qrc': Cannot find file '...\release\osmc_ru.qm'` — qrc от TRANSLATIONS ссылается на `.qm`, которого в пустой папке ещё нет (в обжитой `E:\Builds\tMC` он лежит с прошлых сборок). Лечение: перед `build.bat` создать `release\` и сгенерировать файл: `New-Item -ItemType Directory -Force <build>\release; lrelease translations\osmc_ru.ts -qm <build>\release\osmc_ru.qm` (lrelease — из `QTDIR\bin`).
- Синтетическая тестовая сцена из одних только лесов/парков/площадок не экспортируется: растительность и площадки не создают воксельных чанков — экспорт падает с «Could not voxelize a single object (empty or too huge meshes)». Добавь хотя бы пару зданий (например, по углам прямоугольника) — они задают и границы мира.
- В режиме `--flat` пустые чанки внутри прямоугольника данных землёй не заполняются — «пустых мест» для шага 3.51 почти не остаётся. Проверять шаговый лес/одиночные деревья надо в обычном режиме (без `--flat`): там прямоугольник данных и «дыры» в нём заполняются землёй.
- Генераторы тестовых `.osm`: перевод метров в градусы — `метры / (111320 * cos(lat))` (не `/1000`!). Признаки «сцены, сжавшейся до субблочных размеров» в логе: `Objects: N (skipped: M)` с пропущенными полигонами и `there were 1 m² of forests` в строке «Vegetation topped up».
- Замеры времени шагов: `MCX_LOG_STEPS=файл` пишет строки `[mcx] HH:MM:SS имя <ms> ms`, где `<ms>` — время с момента ПРЕДЫДУЩЕЙ строки (не накопительное). Длительность шага 3.5 — строка `before 3.51`, шага 3.51 — строка `before 3.55`.
- В пробниках по миру: мировые координаты из локальных метров сцены — `worldX = localX − centerX`, `worldZ = centerY − localY` (ось Z перевёрнута; центр — середина bbox данных).
- Региональный файл `.mca` покрывает 32×32 чанка (512×512 блоков): 16 region-файлов (4×4) — это мир до 2048³, а не «маленький». Размеры мира проверяй диапазоном чанков (`xPos/zPos` из NBT), а не числом region-файлов.
- Идентификаторы игровых регистров Minecraft (биомы, сущности, блоки) — НЕ помнить на слух, а сверять с вики minecraft.wiki / официальными чанклогами / файлами игры. Ошибка 1.2.26: биом болота записывался как `minecraft:wetland` — такого ID в игре НЕТ (болото — `minecraft:swamp`); «wetland» — только тег OSM `natural=wetland` и термин «wetland biomes» в вики (группа биомов река/болото/пляж). Быстро не выясняется — спросить владельца (рецепт 5.2 в `.agents/recipes.md`). Игра с несуществующим ID в палитре биомов чанк либо крашит, либо (с модами) молча откатывает — цвета не красятся.
- Лес `vegpol 71111110` площадью ≥5000 м² получает `VegSite::spruce` (см. `8490`–`8500`) — лесной цикл режет его до ~38% клеток сетки («ёлки редкие») НЕЗАВИСИМО от климатической зоны, а в циклe ветка `site.spruce` стоит РАНЬШЕ `zt.jungle`. Признак в мире: «разреженный однотипный лес», а зональная ветка (свои деревья/лианы/большие деревья) не срабатывает вовсе. Порядок веток в лесном цикле: `pale` → `park` → `intra` → `spruce` → зональные.
- Если «нетstats/деревьев меньше ожидаемого» — не вери на глаз: воспроизводи сетку шага 3.5 в Python (`colHash`/`pairKey` — простые, копируются) и сверяй каждую клетку-кандидат с миром. Так за один прогон видно: доходит ли код до ветки, и где гейт режет.
- `QComboBox::setMaxVisibleItems(N)` молча игнорируется, когда для виджетов применена таблица стилей (в приложении qss): попап показывает все пункты. Рабочее лечение: подкласс QListView с переопределённым `sizeHint()` (высота = N реальных строк) через `box->setView()` (setView — до добавления пунктов!). Попап sized by sizeHint — и размер, и место открытия считаются от него.
- Стилизованный комбобокс получает styleHint `SH_ComboBox_Popup=1`: попап выравнивается по ВЫБРАННОМУ пункту — с последним выбранным список растёт ВВЕРХ. Отключать через `QProxyStyle` c `styleHint(SH_ComboBox_Popup) -> 0`, поставленный на УРОВНЕ ПРИЛОЖЕНИЯ (обернуть Fusion в theme.cpp, «свои» комбо помечать dynamic property и смотреть `w->property(...)`). Пер-виджет `box->setStyle()` НЕЛЬЗЯ — он отключает qss приложения для виджета (комбо становится нативно-серым с серым текстом). Двигать окно попапа в showEvent/eventFilter(Show) — ненадёжно (Show приходит поздно/не доходит).
- Правила стилей из qss приложения или от предка-диалога могут молча НЕ доходить до скроллбара попапа комбобокса (окно-попап — отдельное окно). Стиль скроллера задавать НА САМОМ виджете: `view->verticalScrollBar()->setStyleSheet(...)` — применится гарантированно.
- `paletteIndexOf("имя")` при отсутствии имени возвращает -1, и `IdPaletteStart + (-1)` молча совпадает с соседним enum (IdStone) — объект строится булыжником/камнем без единого предупреждения (так торговые автоматы вестибюля и `qPBlk` лаборатории вышли камнем: `minecraft:polished_blackstone` не было в палитре). Перед использованием нового имени через `blk()`/`blkName()` убеждайся, что строка есть в `kBlockPalette`, иначе допиши в конец.
- Зонды, воспроизводящие экспортные хеши (`finHash`/`v30` и т.п.) по координатам из мира: аргументы хеша — часто ЛОКАЛЬНЫЕ координаты объекта (`miny + lyF` = локальный ряд этажа, например 3), а не мировые; угадать офсет по готовому миру нельзя. Достоенный способ получить фактические корзины — временный отладочный дамп из самого экспорта (env-гейт + запись в файл), после замера удалить.
- Имена блоков в палитре зондов сверяй с реальным выводом `blockName`/палетой чанка: кашпо — это `minecraft:potted_*`, а не `flower_pot`; legacy `minecraft:stairs` в сохранённом чанке читается как `oak_stairs`.
- Скриншотные замеры на фейковом экране (`QT_QPA_PLATFORM=offscreen`) — КРАЙНИЙ случай, применять долго (проба с moc/rcc, пересобирается несколько раз): сначала живая проверка (попросить владельца открыть окно), проба — только для того, что глазом не видно: точная геометрия, направление открытия, порядок событий.
  - Фейковый экран маленький (~800×480), аргументы вида `offscreen:size=1920x1080` МОЛЧА игнорируются. Чтобы проверить «влезает/открывается вниз» — прижимать окно к верху фейкового экрана (`w->move(100,0)`) и уменьшать контент пробы (`::item { min-height: 20px }`), а не пытаться увеличить экран.
  - Шрифтов в offscreen нет: высоты строк и текстовые метрики меньше реальных, текст на grab не рисуется (видны только цветные плашки). Геометрия и направление достоверны; наличие скроллбара, тексты и сочетаемость цветов — только в живом окне.
  - Переполнение списка в пробе форсировать явно (докинуть items + `min-height`), иначе `scrollMax=0` и «скроллбар не нужен» — следствие фальшивых строк, а не кода.
  - `rcc x.qrc -o rcc_x.cpp` (Qt 5.15): ресурс регистрируется static-initializer'ом в самом сгенерированном файле; `Q_INIT_RESOURCE(имя)` не звать — функция генерируется без суффикса (LNK2019).
  - Механика: `box->showPopup(); qApp->processEvents();`, читать `cont->y()` против низа комбо, `cont->height()`, `verticalScrollBar()->maximum()/isVisible()`, цвета — `widget->grab().save(png)` (окна показывать не нужно); вывод — в файл, qWarning в консоли не виден.
- Растительность из шаблонов (палые леса: `leaf_litter`, `tall_grass`, ковры) кладётся id из `g_caveStates` (`>= IdCaveBase`), а не enum-константами — `isVegBlockId` их НЕ знала и считала «постройкой»: точечные объекты (скамейки, павильоны, скульптуры) молча пропускались целиком. Проверки «клетка свободна / это растительность» обязаны покрывать и диапазон шаблонных состояний (now: разбор имени `leaf_litter`/`*_leaves`/`*grass*` и т.п. в `isVegBlockId`); стволы (`_log`, `stem`) вырубать нельзя — они настоящие блокеры.
- Плоские многаклеточные объекты (павильон 3×3, стенд 2×2, скамья 1×2) на холмистом рельефе: уровень пола брать как МАКСИМУМ `surfaceTop()+1` по всему футпринту (не от узловой колонки), иначе соседние колонки оказываются «заняты землёй» и объект никогда не строится; низкие колонки до уровня пола добывать цоколем (тот же материал пола).
- Вложенный `switch` внутри `case` внешнего: `break` в обработке выходит только из ВНУТРЕННЕГО switch — счётчики/общий хвост кейса после внутреннего switch выполняются повторно (так пропущенная скульптура засчитывалась построенной, и placed+skipped давало N+1). Вложенные развилки в кейсах писать флагами/ранними выходами, счёт инкрементировать ровно в одной ветке.
- GCC строже MSVC и падает там, где MSVC прощает (проверено на сборке Linux): (а) вложенный struct с инициализаторами-по-умолчанию НЕЛЬЗЯ использовать как аргумент по умолчанию функции того же класса (`= WorldOptions()` → «default member initializer required before the end of its enclosing class»; `Inner() = default` и `= {}` не помогают) — лечится выносом struct на уровень файла + `using`-алиас внутри класса (алиас сохраняет `McWorldExporter::WorldOptions` и агрегатную инициализацию `{seed, true}`, пользовательский конструктор её ломает); (б) нужны прямые include'ы: `std::numeric_limits` → `<limits>`, `QPointF` в заголовке → `<QPointF>` (Qt даёт только forward-declaration). Искать такие места — `g++ -fsyntax-only` по каждому заголовку за один проход, а не regex-аудитом.
- `QProcess::setNativeArguments` (нужен для `explorer.exe /select,"файл"`) существует ТОЛЬКО в Windows-сборке Qt — весь блок под `#ifdef Q_OS_WIN`; на Linux «показать файл в папке» делают через `QDesktopServices::openUrl(QUrl::fromLocalFile(папка))`.
- Миры НЕ совпадают побайтово даже между двумя прогонами ОДНОГО `osmc.exe` с одним `--seed` (сущности, животные, случайная окраска — RNG по времени): сверять миры «CRC каждого файла» нельзя, нужен контроль «тот же exe, тот же seed, два прогона». При этом соли structure_set (`findPlacementSalt(seed, chunk)`) детерминированы — на Linux 3 из 5 «руинных порталов» получили другие чанки при том же seed: кандидат на разбор (FP-контракт FMA у GCC / порядок обхода контейнеров), решение за владельцем.
- ⚠️ Палитры секций в мире формата 26.x используют ключ `id`, а НЕ `Name` (`{'id': 'minecraft:air'}`); свои python-разверки чанков обязаны читать `e.get('Name') or e.get('id')` (см. tests/tools/verify_mc_export.py — он нормализует сам). Односторонний поиск по `Name` молча теряет бо́льшую часть блоков (в самостоятельных проверках мира база « потеряла» стену: 607 колонок вместо 5379).
- ⚠️ Якоря, рождённые ВОКСЕЛИЗАЦИЕЙ (списки `VoxelOut`: chests/paints/npcs/... и `halfDoors`), живут в ДО-СДВИГОВЫХ координатах: после обзора рельефа весь мир поднимается на `yShift` (`store.translateY` + цикл подъёма каждого списка в exportrun.cpp, строка ~8060). Новый список без строки в том цикле даёт якорь под землёй (так floor_half получил дверь на y=67 при траве 79 и стенах 80..139). Любое новое поле в `VoxelOut` с мировым y ⇒ добавить `+= yShift` в блок `if (yShift != 0)`. Якоря exportrun (`surfaceTop()` и спутники) сдвига не требуют — они считаются после.
- ⚠️ JSON advancement'ов датапака писать ТОЛЬКО в схеме целевого формата, а схему смотреть из ванильных данных версии (клиентский jar, `data/minecraft/advancement/*.json`; в серверном jar ванильных advancement'ов нет): 26.x (pack format 101+) читает поля `conditions` (`entity`, `location`) как ОДНО условие с диспатчем `"type"` и пространствами имён в ключах предиката (`"minecraft:entity_type"`); 1.21.x (48..100) — как МАССИВ условий с диспатчем `"condition"` и простыми ключами. Теги `#ns:x` разрешаются внутри предикатов в обеих семьях, но не в полях, парсящих как простой ResourceLocation. Один битый advancement рвёт ВЕСЬ реестр `minecraft:advancement` ⇒ мир открывается safe mode («reset to vanilla with --safeMode»); тот же реестр роняют неизвестные id сущностей/триггеров (сверяй по jar) и просто недостающая `}`.
  - Локальная достоверная проверка — `py -3 tests/tools/server_check.py 26|121 <zip>`: сервер печатает тот же WARN и по элементом логу `Errors in element osmc_enc:<id>` показывает виновника. Для 121 нужен экспорт `--format 1.21` (legacy level.dat): на 26.x-формате 1.21.11 падает раньше с «No key dimensions in MapLike[{}]» — это не датапак виноват.
  - Версионно-зависимые JSON — оверлеями или ветками по формату (образец: `export/highworld.cpp`, граница 101 = 26.1); `pack.mcmeta` писать всеми стилями ключей сразу: `pack_format` + `supported_formats{min,max}_inclusive` + `min_format/max_format [major,minor]`.
  - Ручную склейку JSON в строках C++ проверять python-зеркалом со `json.loads` ДО сборки (на этой задаче зеркало поймало двойную запятую и недостающую скобку за секунды вместо цикла сборки).
- ⚠️ В Minecraft ДВА разных реестра «на что можно подписаться»: триггеры advancement'ов (`criteria.trigger`) и статистические критерии целей `scoreboard objectives add <obj> minecraft.mined:<block>` (есть crafted/used/broken/picked_up и т.п.). В реестре триггеров обоих семейств (вычитан из классов `CriteriaTriggers`/`aj` серверных jar 26.3 и 1.21.11) триггера поломки блока НЕТ — зато `minecraft.mined:minecraft.glass` и `minecraft.mined:minecraft.glass_pane` работают в обеих (живая проверка владельца + server_check). Вывод «такого id в игре нет» делать только переглядев ОБА реестра. Так теперь считается ужас города: счётчик статистики игрока вместо запечённых координат окон (перепись не досчитывала половину домов; статистика видит каждое разбитое стекло за тик).
  - Принят ли критерий — смотреть в `scoreboard.dat` мира после server_check: objective появляется только если критерий распарсен; `say` в load-функции НЕ доказательство (упавшая команда внутри функции не рвёт её и не пишет в лог). Файл лежит по-разному: 26.x — `data/minecraft/scoreboard.dat`, 1.21.11 — `data/scoreboard.dat` (без подпапки minecraft).
  - Семантика консоли/функций для самописных харнессов: `execute as <оффлайн-имя>` не резолвится (функция не выполняется), консольный `@s`/`set @s` в 26.x не принимается; симулировать игрока можно сущностью: `summon` + селектор с координатами (`@e[type=minecraft:armor_stand,x=-8,y=0,z=-8,dx=16,dy=112,dz=16,limit=1]`) — 26.x молча ИГНОРИРУЕТ NBT `Tags:[...]` у summon, искать потом по тегу нельзя; у сервера НЕТ загруженных спавн-чанков — summon без предварительного `forceload add` сажает сущность в выгруженный чанк, и следующий селектор отвечает «No entity was found» (команда summon при этом УСПЕШНА).
  - `execute if score #x matches 1` БЕЗ `<objective>` — функция целиком не парсится: в логе `Failed to load function ... whilst parsing command on line N` (нумерация с учётом комментариев); server_check это ловит.
  - ⚠️ Спецификатор времени (`schedule`, `clear -s`, ...): единиц только `d`/`s`/`t` — МИНУТ (`m`) НЕТ, «минуты» пишут в секундах (`180s`). `schedule ... 3m` даёт `Invalid unit at position N`, функция не парсится (26.x — шквал `Failed to load function`, 1.21.11 — «Failed to load datapacks, can't proceed», мир не открывается); server_check ловит обе семьи.
- ⚠️ Офлайн-развёрка чанков своим python'ом (без сервера): компактная палитра упаковывает long'ами по `floor(64/bits)` записей в long НЕЗАВИСИМО от того, делит ли bits на 64 (`per = 64 // bits`, остаток бит до дна long пропадает) — формула `512//bits` даёт мусор в координатах и «пропавшие» блоки; индекс клетки `y%16*256 + z%16*16 + x%16`. `level.dat` в zip экспорта лежит gzip'ом (начинается с `0x1F 0x8B` — `zlib.decompress` падает «incorrect header check», нужен `gzip.decompress`), а спавн 26.x хранит НЕ в `SpawnX/Y/Z`, а в `Data.spawn.pos`.
