## 2а. Справочник по экспортёру: где что искать (читай нужный подраздел под свою задачу)

Подразделы названы по задачам: найди тот, что соответствует просьбе владельца, и читай именно его. Номера строк не указываю (они плавают) — ищи по **именам функций и ключевым английским словам комментариев** через `grep`. Файл `export/mcworldexporter.cpp` целиком не читай.

### Как сшиваются здания из нескольких частей (building:part, комплексы, башня на подиуме, висящие части)
Цепочка из трёх этапов, каждый в своём месте:
1. **Чтение и привязка частей — `input/tmcproject.cpp`, блок с комментарием `BUILDING PARTS (building:part)`.** Правила кладут часть в слой `bldpol` с `PART=1`. Дальше: каждая часть привязывается к «хозяину» (контуру здания) по пересечению площади (≥30% части); контур хозяина уменьшается на объединение частей (`Difference`); если от контура почти ничего не осталось — удаляется. Часть наследует код (`CODE`), материал (`MAT`) и адрес хозяина; адрес получает только самая большая часть. Метка `PART` после блока становится `part` (нужна экспортёру: мелкие части получают тонкие стены).
2. **Поднятые части (`min_height` / `building:min_level`) — тот же файл + `osm_rules.json` (правила «raised above the ground») + `scene/mcscene.cpp`.** В `addObjects` считается `MINH` (высота основания в метрах; по этажам — этаж из `height/levels` или 3.3 м). Блок «Raised parts (MINH, meters)» после блока частей превращает `REL` (высота верха) в толщину части: `REL = max(3, верх − MINH)`. `default.t3d` поднимает основание по полю `MINH` (`liftField`), `mcscene.cpp` ставит `McObject::raised` (метры).
3. **Склейка и построение — `export/mcworldexporter.cpp`:**
   - `raiseLowBuildingParts` — низкие части подтягиваются до ≥7.6 блока;
   - в `Export()` после него — вычисление `thin` для мелких частей (стены в 1 блок: флаг `thinW` в `voxelizeObject`);
   - **`mergeIndustrial`** — главная сшивка: касающиеся или перекрывающиеся здания **одного кода** склеиваются в один объект (`merged=true`, объединённый меш). Кандидаты: `mergeableCode()` (промзона 44340000, церковь 44319000, нежилые 44310000…44318000), любые поднятые части, а жилые 44400000 — только если над ними висит поднятая часть и планы пересекаются. Лимиты: габарит ≤140 блоков, ≤60 частей. У склейки поле `raised` = минимум по частям, `floatCols` = колонки, над которыми только висящие части (земля под ними не поднимается);
   - в **`voxelizeObject`**, блок `if (obj.merged)`: внутренние стены между телами (по осям X и Z) и **перекрытия между телами друг над другом (ось Y)** удаляются — внутреннее пространство общее; этажи и лестницы кладёт обычный проход по всему «столбу»;
   - отдельный объект с `raised>0` (не склеенный) строится «парящим» (`raisedObj`: без фундамента, входа, подвала, без записи в `colMin`);
   - проходы после `flushJobs()`: **нижний ряд стен висящей части из светло-серого бетона** (комментарий `The bottom row of the walls of a raised part`), **стремянка в висящую часть** (`Access to the raised building parts`: шахта через плиту + лестница, только внутри здания), купола, односкатные крыши.
4. Склейки лифтовых шахт (`LIFT=1`) устроены отдельно: `liftJobs` — шахта строится после всех зданий и только выше крыши своего здания.

### Как устроены правила экспорта: OSM-теги → слои → коды (`osm_rules.json`)
- Файл `resources/osm_rules.json`, читает `osm/tmcosmrules.cpp` (`TmcOsmRules::classify(from, tags, pass)`), применяет `input/tmcproject.cpp` (функция `addObjects` и окружающий цикл по слоям GDAL `points`/`lines`/`multipolygons`).
- Правило: `from` (слой драйвера OSM), `when` (условия по тегам: значение, `"*"` тег есть, `"-"` тега нет, `"!v"`, списки, `"~re"` регулярка, числа `">=4"`, служебные `_area`, `_perim`, `poi:<тег>`, `area:<тег>`, `nb:*` для второго прохода), `layer` (`bldpol`, `vegpol`, `vgbpol`, `csrpol`, `hdrpol`, `hdrlin`, `rdslin`, `rrslin`, `rdcpol`, `blkpol`, `csrpnt`/`hdtpnt` — точечные объекты, `mrspol` — болота, `-` = не брать), `fields` (шаблоны `{тег}`, `{тег1,тег2}`, `||` — запасной вариант), `as` (`polygon`, `line`, `crosswalk:N`, `square:N` — преобразование геометрии). Срабатывает **первое** подходящее правило сверху, если нет `"continue": true`. Подробное описание — раздел `_help` в начале файла.
- **Коды `CODE`** — это тип объекта (список — `resources/heights.csv`): 44000000 сарай; 44310000 нежилое; 44311000 администрация; 44312000 школа; 44313000 детсад; 44314000 больница; 44315000 НИИ; 44316000 культура; 44317000 музей; 44318000 торговый центр; 44319000 церковь; 44340000 промзона; 44400000 многоквартирный дом; 44400002/44400100/44400110 частный сектор, дачи, коттеджи (скатная крыша); 31xxxxxx вода; 45xxxxxx/61xxxxxx дороги; 71xxxxxx растительность. Код определяет облик в `export/mcworldexporter.cpp` (ищи `obj.code ==`).
- **Высота `REL`**: `"REL": "auto"` → `osm/tmcrel.cpp: tmcAutoRel` (тег `height` → `building:levels` по формулам этажей → типовая по коду из `heights.csv` → 6 м). **Материал `MAT`** — из `building:material` / `building:facade:material`; в экспортёре — `materialBlockId()`.
- **Два прохода**: правила с `"pass": 2` видят только то, что не опознал первый проход.
- Служебные поля, которые добавляет `tmcproject.cpp` поверх правил: `MINH` (высота основания), `PART`, `ROOF` (`onion`/`skillion`), `ROOFH` (`roof:height`), `ROOFD` (`roof:direction`), `ROOFC`/`ROOFM` (`roof:colour`/`roof:material` купола), `TYSTR`/`STREET`/`NUMBR` (адрес, `osm/tmcaddress.cpp`).
- Чтобы новое поле дошло до блоков: правило/`tmcproject.cpp` → имя поля в `L->fieldNames` → чтение в `scene/mcscene.cpp` (`ExportItem` → `McObject`) → использование в `mcworldexporter.cpp`.
- Если нужно, чтобы не было правила под тег — проверка `--dry-run` и переменная `TMC_OSM_UNMATCHED=файл.tsv` покажут необработанные объекты.

### Как здание превращается в блоки (`voxelizeObject`)
Функция `voxelizeObject` (в `mcworldexporter.cpp`) вокселизует один объект: растеризует треугольники меша в сетку (`grid`: 0 воздух, 1 поверхность, 2 внешний воздух, 3 тело, 4 внутренняя обшивка, 5 лестница/шаг), заливает внутренность «flood fill» снаружи, делает полость с оболочкой в 2 блока. Дальше по порядку (ищи по комментариям): стены (`structFor` — фундамент, 2 нижних и 2 верхних ряда из `structId`), окна (**`windowDir`** — профили: жилые 1×2/2×2, нежилые 2×3 `bigWin`, торговые центры панорама `panor`, материал «стекло» панорама `panoWin`; в двух верхних рядах колонки окон нет), входы (`BUILDING ENTRANCES`), этажи и перекрытия (`Inter-floor slabs`), лестницы между этажами (`Inter-floor stairs`, при нехватке места — стремянка), перегородки (`partitions`), мебель и интерьеры (`"Interiors" v2`), сундуки/спавнеры/жители, подвалы (`BasementSite`), крыши частного сектора из ступеней.
- Объекты строятся параллельно (`VoxJob`, `flushJobs`), результаты сливаются **в порядке объектов**: более поздний объект перекрывает ранний.
- `decorateWalls` — цветные полосы детсадов (без жёлтого/оранжевого), белые вертикали школ, красные пояса НИИ.
- Фундамент: `sink` (2 блока в землю; частный сектор и сараи — 1), рост по высоте `extraBlocks`. Здание помечает колонки в `colMin`/`colAnchor` — по ним земля под зданием поднимается/выравнивается.

### Как строятся крыши (купола, односкатные, скатные)
- Плоская крыша — верхние 2 ряда оболочки. Частный сектор (44400002/44400100/44400110) — двускатная крыша из ступеней (внутри `voxelizeObject`).
- **Купола** `roof:shape=onion|dome` и **односкатные** `skillion` — проходы после `flushJobs()` в `Export()`: комментарии `Domes of churches` и `Monopitch roofs`. Купол: цвет по `roof:colour`/`roof:material` (ближайший бетон; **белый — полированный кварц `smooth_quartz`, не бетон**; без цвета и известного материала — **простой серый бетон**, без шпиля; шпиль только у жёлтого/золотого, синего, голубого, красного, чёрного — золото/лазурит/алмаз/редстоун/уголь; стекло — полусфера, потолок под ней вырезается). Односкатная: клин от нижнего края к верхнему по `roof:direction`, высота `roof:height`. Тело под такой крышей ниже на `roof:height` (правка `REL` в `tmcproject.cpp`).
- Новые формы крыш добавляй так же: поле из тегов в `tmcproject.cpp` → `McObject` → отдельный проход в `Export()` по готовому `store`.

### Земля, вода, дороги, мосты, железные дороги
- Земля (`step 3`, комментарий `3. Ground`): колонки всех затронутых чанков; `groundTopCol(x,z)` — уровень поверхности; `colMin` поднимает землю под зданиями (не выше +3 блоков над естественным уровнем), `colWater` — карта «колонка → глубина водоёма», `colWool` — площадки `csrpol`/покрытия (бетон/шерсть вместо дёрна), `roadCols` — дороги, `paleCol` — лес скрипунов, `makeGround` — сборка `GroundChunk` (верх, поверхностный блок, вода).
- Дороги `rdslin`: ленты → ковёр/бетон с разметкой и зеброй; `roadsHigh`/`roadsLow`, `paintBody`, `roadCols`. Железные дороги `rrslin` — рельсы по оси (`railCellChain`, `railShapeFor`). Метро (61123100): перед `railCellChain` полилиния **спрямляется** в диспетчере (реальные линии — длинные диагонали, сетка превращает их в лесенку с поворотом на каждом блоке): каждый диагональный участок идёт 10 блоков ПРЯМО, потом 20 блоков ДИАГОНАЛЬЮ back toward the real mapped line (`rc=min(1, 1.5·dc/da)` — возврат meets the true line ровно в узле); при отклонении ≤1 блока участок просто повторяет исходную OSM-полилинию до узла; узлы (станции/перегибы) остаются на месте. ЗОННЫХ guard'ов больше нет — линии можно поворачивать где угодно. Проход тоннеля строит оболочку **двумя фазами**: сначала union-карты по ВСЕМ цепям (`tInt` — колонки интерьера, глубокий пол+`maxFloor`+`minU`; `tWallLo/Hi` — ряды стенки [min..max]), затем запись: интерьер всегда побеждает стенку (иначе стенка соседнего пути стояла в чужом коридоре «колонной»), пол — самый глубокий, скругление `minU==2` только там, где ничей более широкий интерьер. Колонка, занятая цепями с разными этажами, не затирается чужим «восстановленным камнем»: интерьеры этажей прорезаются раздельно, при разнице этажей ≥5 между ними — плита пола верхнего этажа (иначе верхний коридор запечатывался породой нижнего — «колонны» на реальных пересечениях двух путей). Угловая клетка цепи заявляет СЕЧЕНИЯ по обеим осям (входа и выхода) — сечение только по оси выхода оставляло 3 колонки породы за поворотом внутри коридора (те же «колонны» на каждом изгибе). Уступ уровня не ставится на поворот (`railShapeFor` даёт уклон только на прямых; угол принудительно плоский, несколько раундов клампа). Оболочка пишется до ВСЕХ рельсов всех цепей; рельс нависает над чужим более глубоким коридором — под него подпора из `floorId`.
- Электрификация рельсов: `electrifyRails` (хелпер рядом с `railShapeFor`) — каждый 20-й рельс становится `powered_rail`, но ТОЛЬКО на прямой цепочки; «попадание» на поворот переносится дальше и ставится подряд (2–5 штук). ПОД КАЖДЫМ `powered_rail` кладётся `redstone_block` (заказ: «чтобы электрофицированные рельсы были всегда активны») — рельс на редстоуне не переходит в тормозящее состояние; редстоун пишет тот же `electrifyRails` сразу после смены рельса (все три места вызова накрыты). Срабатывает для метро (проход тоннеля), наземных путей с полем `ELEC`≠no (колонка `ELEC` из `osm_rules.json` → `McObject::railElec` через `mcscene.cpp`) и трамваев 61124000 (всегда). Балласт: `railBedCols` (колонка → блок) заполняется в диспетчере рельсов, `makeGround` кладёт его в поверхностный блок вместо дёрна (камень под электрофицированными, каменные кирпичи под трамваями; дорога/вода не перекрываются).
- Мосты через воду — комментарий `BRIDGES` после `lap("g4 ground fill")`: настил, балка из каменного кирпича, опоры каждые 12 блоков.
- Рельеф и склоны: `heightAt`, `terrainTopBlock`, плоскость мира (`planeSamples`), край-«фаска» перехода к игровому миру (`3.59b`).

### Как устроены тоннели метро и залы вокзалов (метро 61123100, вокзал 44330000)
- Классификация: `railway=subway`+`tunnel=yes` → код 61123100 (слой `rrslin`), `building=train_station` → слой `bldpol` код **44330000** (правило в `osm_rules.json` стоит ПРАВЕД правила школы; высота 12 м в `heights.csv`). Так же опознаётся `building=transportation`: правилом в `osm_rules.json` (рядом с train_station) если есть тег `subway=yes`, и в `tmcproject.cpp` (блок перед `isBld`; правила — только по тегам, близость они не меряют) — если в 10 блоках от полигона есть точка `railway=subway_entrance`; у transportation без rules-правила code пуст — там же синтезируется классификация вручную (CODE/REL/MAT из тегов).
- **Prescan станций** в `Export()` перед диспетчером (`struct StationSite`/`stations`): bbox и центр вокзала берутся из **`vertices` меша** — у полигональных зданий `paths` пуст (он заполнен только для парковок/линий) — через `toBlockX/toBlockZ`.

- **Входная шахта — СТРОГО ВНУТРИ здания; в большом здании — В ЦЕНТРЕ ЗАЛА, иначе в углу; вся конструкция не режет фасад** (`ringLv` — уровни размещения). Приоритет для НЕ-canopy и canopy одинаков: `saC=clamp(aCt,wA0,wA1)`, `sbC=clamp(bCt,wR0,wR1)` в ±1 от цели + `shaftFree` всего кольца → шахта в центре (заказ: «лестница буквально в центре зала»); цель — центр зала (`aCt=ac−2`, `bCt=bc`), а для canopy ЦЕНТР СНЕСЁННОГО ПАВИЛЬОНА (`aCt=(aB0+aB1−4)/2`, `bCt=(bB0+bB1)/2`); если линия пересекает центр — угловой перебор ниже. Единственное правило: шахта с лестницей НЕ ПЕРЕСЕКАЕТ линию; если свободно нигде (Курская-спираль) — `ringLv=0`, зал без входа. Окна: не-canopy вдоль зала `sa0∈[max(A0+1,aB0+2), min(A1−5,aB1−6)]` (3-клеточный коридор наружу тоже остаётся в здании); canopy — фасад снесён, окно = сам зал `sa0∈[A0, A1−4]`, `bS∈[B0+3, B1−3]`, голая яма запрещена (дыра в площади без забора — опасность). Кандидаты поперёк (`bS`) жмутся к дальней стене в клетке от неё — для кольца `ringLv=2` окно `[max(B0+3,bB0+4), min(B1−3,bB1−4)]`; для голой ямы `ringLv=1` (кольца нет — оно резало бы фасад) `[max(B0+3,bB0+3), min(B1−3,bB1−3)]`; кандидат чередуется битом 0 хеша `sSide = colHash(pairKey(center)^0x51DEull)` (шахта на стороне, ОБРАТНОЙ смещённым рельсам), затем противоположная сторона, затем середина окна; пре-чек `shaftFree` для ВСЕХ вариантов (canopy тоже) проверяет ВСЁ КОЛЬЦО (`saCs−1..saCs+5`, `b±3`; голая яма `b±2`) на пересечение с `openCols`/`trackCols` (копка ямы `fy+1..orig+2` стёрла бы живые рельсы). Если кольцо не лезет — яма без кольца; если не лезет и яма с коридором — `ringLv=0`: входа нет, прорезать фасад нельзя. `lowEnd` (конец вдоль зала) — бит 1. Котлован **5×5** прорезается ЦЕЛИКОМ сам (`fy+1..orig+2`), `g.top` через `dropTop`; всё (`if (ringLv)`) под гардом, кольцо — под `ringLv==2` (цикл через условие `ringLv == 2 && a <= sa1+1`), двери/портал тоже. `inShaft` возвращает false при `ringLv==0`.
- **Лестница шахты — МАРШЕВАЯ (как в многоэтажных домах), fallback-стремянка удалена**: `nFl = (topS−fy+2)/4` маршей, `placeFlight(f, steps)` — пролёт **2 блока шириной** из `IdBrickStairsN/E/S/W` (facing = направление подъёма; axisX ? E/W : S/N, sign — forward/back) вдоль длинной стороны ямы, чередование сторон, пролёт занимает 4 ряда; в конце пролёта — **полноразмерная площадка** `pL = sa0 (back) / sa1 (forward)` на row `rL` на ВСЮ ширину ямы (solid `masId` — «перекрытие» между маршами). Первый пролёт начинается на клетку раньше площадки (`p = sa0+j / sa1−1−j`). Чётность `invert` подбирается так, чтобы последняя площадка (с ней дверь `exa = pL±1` в кольцо/стену ямы) оказалась НА САМОЙ ДВЕРНОЙ ЛИНИИ `ga` — дверь, портал и коридор стоят в одном ряду (`exa == ga`). Последняя марш укорочена (`steps = topS − rAbs`), верх площадки `topS−1`; `topS = max(origTops по пит)+1` — блок площадки занимает РЯД самой поверхности, выход ВОВРЕНЬ с землёй, в портал входят, а не запрыгивают (жалоба заказчика); пол наружного коридора вровень с площадкой (`topRow = rL+1`). В СЕРЕДИНЕ КАЖДОГО МАРША (`steps≥3`) — барьер **2×1**: клетки `pM..pM+1` (front `pM=sa0+1`, back `pM=sa1−3`), `b=bS`, row `rAbs+1`, тот же `masId[colHash(ck ^ (y·31+0x2E17)) % 8]`, и **факел** `IdTorch` сверху (`rAbs+2`) — новый элемент enum (напольный `minecraft:torch`, добавлен перед `IdCaveBase`): щель между полосами маршей была бесплатным падением до дна шахты, а полноформатное центральное ребро (раунд 3) перекрывало сами пролёты (заказ раунда 4: «2*1 блок в центре пролета, повесь факелы»).
- **Canopy (навес)** — здание-павильон, в который лестница с тамбуром НЕ влезает: `extrudeH∈(0.5,9] && min(w,h)≤12` на prescan (`st.canopy`). Раунд 4: canopy строит СТАНДАРТНЫЙ вход, ИДЕНТИЧНЫЙ внутрезданному — яма + кольцо + коридор + портал (гардов `&& !canopy` больше нет): фасад снесён, поэтому окно = зал (`sa0∈[A0, A1−4]`, `bS∈[B0+3, B1−3]`), голая яма запрещена; кандидаты от ЦЕНТРА хибары (тот же центр и в приоритетном центре-блоке), `shaftFree` проверяет всё кольцо; снос здания (bld±1, rows top+1..+14, высота из `origTops`, а для колонок вне прямоугольника зала — из ground-чанка; снос ПОСЛЕ размещения шахты: нет места под шахту — здание остаётся и входа нет). Дверь `ga` у canopy стоит на улице: проём `fy..fy+8` без зала за ним остаётся породой (безвредно), игроку служат яма-колодец, коридор `e=0..2` с плитой вровень с землёй и портал в ряду `ga`.

### Объекты из точек (`modelField` source'а) и биомы (`effect` source'а)
- Ни имён слоёв, ни хардкода в коде: роль слоя задаёт **сам source в 3D-настройках**. `VectorSource::modelField` (имя колонки с кодом объекта, у точек — «CODE») → `McObject::Spot` (Kind=9); `ModelEffect::Swamp` (бит 128) на source → `McObject::Biome` (Kind=10). В `default.t3d` так объявлены `csrpnt`/`hdtpnt` (modelField «CODE», isGround) и `mrspol` (effect 128, isGround, болота `natural=wetland`). Старые чужие `.t3d`/`.tmc` этих слоёв не содержат — и новых объектов у них нет (осознанно: всё через настройки, без хардкода).
- Правила точек используют `as: square:N` (квадрат N метров вокруг узла, центр — сама точка). CODE правила не несут REL/высот — source «на земле».
- Модель структуры: `mcscene.cpp` читает колонку `modelField` у каждого feature и ищет её код в таблице `resources/point_models.csv` (`код;модель`, рядом с exe, грузится `loadSpotModels` по образцу `heights.csv`); кода нет в таблице — объект пропускается с предупреждением (счётчиком). Номер модели доходит до экспортёра как `McObject::model`.
- Квадрат — только якорь: в диспетчере объектов ветка `o.kind == McObject::Spot` берёт растеризованные колонки (`pre`), центр bbox — якорь (`spots`), а колонки bbox+3 помечает в `noTreePadCols` — деревья не лезут на объект (проверка и в лесном цикле, и у одиночных деревьев).
- Строит шаг **3.575** (после уличной мебели 3.57, до 3.59), `switch (sp.model)` по константам `SpotModel`: 1 (`kStatue`) мемориал — 6 вариантов по хешу колонки, 2 (`kStele`) стела — 3 варианта, 3 (`kFountain`) фонтан (каменное кольцо, бассейн, столб; на столбе источник IdWater, стекающая вода по 4 сторонам — `IdWaterFalling` = water level=8 через `blockProperties`), 4 (`kTower`) вышка (основание iron_block, шпиль IdCobbleWall, 3 кварца), 5 (`kComposter`) компостер. Основание `surfaceTop+1`; под якорем вода/проезд/структура → пропуск. Исключение — вышка: на здании (`colMin`) она растёт от крыши (скан колонки сверху вниз до первого плотного не-растительного блока), при высоте здания ≥32 блок — тело 6 блоков + 3 кварца, иначе тело домножается до ~32 от земли.
- Биом-оверлей: ветка `o.kind == McObject::Biome` в диспетчере только собирает растеризованные колонки в `swampCols` (никаких якорей/падов, polygon не строится). Дальше два места: в лесном цикле шаг 3.5 ветка `swampCols.contains(ck)` (СТОИТ после pale-ветки, до park/intra/spruce) — любой лес под болотом становится рощей болотных дубов (~50% сетки); и отдельный проход перед `lap("before 3.51")` — голые болота редкими дубами (~40% ячеек сетки 6×6) и флорой (dead_bush/fern/коричневые и красные грибы, ~7% колонок); оба места пропускают `colWater`/`roadCols`/`colMin`/`noTreePadCols` и занятые колонки. Болотный дуб — лямбда `plantSwampOak` (дуб с плоской кроной); лозы — `jungleCrownVines`/`vineColumn` с параметром `leafId` (по умолчанию jungle).

### Скрытые структуры: подземелья церквей и лабораторий, стронгхолд, Древний город, лес скрипунов, аванпосты, парящие острова
- Шаблоны (`resources/templates/*.bin`, **не трогать**) читают классы `CaveSet` (пещеры), `LairSet` (`lair_structures.bin`: стронгхолд и Древний город), `PaleDonor` (`pale_garden.bin`, `patch_*.bin`: особняк, аванпосты, лагеря, кораблекрушения). Нет шаблона — функция пропускается, причина в `Result::lairInfo`.
- «Роль» здания (`deepRoleOf`): 1 — точка стронгхолда, 2 — точка Древнего города, 3 — крупнейшие школы; подземелья — лямбды `buildChurchDungeon` (церкви) и `buildLab` (НИИ/школы) в конце `Export()` (`BasementSite`).
- Парящие острова над парками/детсадами — `IslandSite`, комментарий `Floating islands`; лес скрипунов — шаг `g0`…`g3` (`lap("g1 Pale Garden/donor")`).
- Датапак поиска структур и `level.dat` — `WorldOptions::locateDatapack`, раздел записи (`step 5`).

### Материалы, блоки, палитра, цвета, стекло
- Палитра: массив `kBlockPalette` (имя блока + RGB) в начале `mcworldexporter.cpp`; `IdPaletteStart + paletteIndexOf("minecraft:...")` — id блока; специальные блоки (с состояниями: двери, лестницы, ковры, лианы…) — перечисление `enum` выше и функции `blockName`/`blockProperties`. **Новые блоки в палитру — только в конец.**
- Цвет здания: `nearestBlockId(QColor)` — **только бетон** (`_concrete`) по ближайшему RGB; материал `MAT` — `materialBlockId()` (кирпич, камень, дерево, бетон, **стекло**, металл…). Особые коды: церковь — каменный кирпич, НИИ — каменный кирпич, частный сектор — кирпич/брёвна по наличию перекрытия.
- Материал «стекло»: стены бетонные (`structId`), окна панорамные как в торговых центрах, внутри и перекрытия бетонные.
- Цвета декора подбирай так, чтобы не совпадали с цветами, на которые смотрят проверки `tests/tools/verify_mc_export.py`.

### Порядок работы `Export()` (конвейер целиком)
1. Старт: загрузка шаблонов (`CaveSet`, `LairSet`, `PaleDonor`), размеры области и преобразование координат `VxTransform` (`tf`).
2. Вокселизация объектов по ролям (`McObject::Kind`: здание, растительность, дорога, рельсы, площадка, вода, парковка, покрытие); `flushJobs`; проходы после неё (бетонное кольцо висящих частей, стремянки, купола, клинья крыш).
3. Земля (`g0`…`g4`), мосты.
4. Растительность `3.5`…`3.6`, уличная мебель `3.57`, точечные объекты `3.575`, ограды `3.58`, подземелья/деревни/вывески (`beginStep(10)`).
5. `4.` чанки → региональные файлы `.mca`; `5.` zip-сохранение (`level.dat`, датапак, `ATTRIBUTION.txt` для данных OSM).
- Замеры времени шагов: `lap("...")`, `tmcStepLog`.

### Отладка и диагностика
- Логи: `--log файл.txt`; `--dry-run` — загрузка и классификация без постройки мира; `TMC_OSM_DEBUG=1` — строка на каждое здание (какие теги увидели правила, слой, код); `TMC_OSM_UNMATCHED=файл.tsv` с `--dry-run` — необработанные объекты.
- Проверка блока в мире: `tests/tools/verify_mc_export.py` (`chunk_iter`) и скрипты рядом (`find_block.py`, `scan_*.py`).
- Тестовая сцена: `tests/data/osm_buildings.osm`; её можно править копией (в `C:\Temp`) — например, добавить тег `building:material=glass` или `roof:shape=dome`, и посмотреть срез результата.

## 5. Рутинные задачи — пошаговые рецепты

### 5.1. Изменить поведение экспортёра (блоки, формы, цвета)
1. Найди код: `grep -n "ключевое_слово" export/mcworldexporter.cpp`. Комментарии в коде английские — ищи по английским словам (`roof`, `window`, `entrance`…).
2. Прочитай **только** нужный участок (±60 строк). Посмотри, как соседний код решает похожую задачу, и повтори стиль.
3. Блок по имени: `quint16(IdPaletteStart + paletteIndexOf("minecraft:имя_блока"))`. Блока нет в палитре `kBlockPalette` — **допиши его в конец массива** (не в середину!) с RGB-цветом.
4. **`store.set(x,y,z, IdAir)` ничего не делает** (воздух игнорируется). Чтобы убрать блок — `store.erase(x,y,z)`.
5. Соберись, прогони тесты, посмотри результат на тестовой сцене (раздел 4).
6. Запиши изменение в `CHANGELOG.md` (раздел 7).

### 5.2. Добавить или изменить правило OSM (`resources/osm_rules.json`)
- Формат описан в разделе `_help` самого файла. Правило: `from` (`points`/`lines`/`multipolygons`), `when` (условия по тегам), `layer`, `fields` (`CODE`, `REL`, `MAT`…).
- **Неоднозначное сопоставление с Minecraft — через вики, не через память:** если непонятно, какому биому/существу/блоку/ID в игре соответствует OSM-тег (пример: `natural=wetland` — это игровой болотный биом, но НЕ `minecraft:wetland`), сначала быстро изучи нужный раздел вики minecraft.wiki (названия и ID там должны совпадать с игрой буквально). Быстро не выясняется однозначно — **спроси у владельца**, что делать, и не выдумывай. См. §8 про wetland/swamp.

## 7. Версия, журнал изменений, релиз

- **`CHANGELOG.md`** (английский, формат «Keep a Changelog»). Любое заметное для пользователя изменение — строка под `## [Unreleased]` в разделах `Added` / `Changed` / `Fixed`. Не нужно записывать чисто внутренние правки без видимого эффекта.
- **Версия** — строка `VERSION = ...` в `osmc.pro`, формат `1.2.YY.MMDDN`: `YY` — год, `MMDD` — месяц и день, `N` — номер сборки за день (1–9). Пример: `1.2.26.10283` — третья сборка 28 октября 2026. Меняй **только эту строку** (через замену строки, не переписывая файл). Увеличивать версию **только когда владелец просит собрать релиз.** Major/minor не трогай без прямой просьбы.
- После смены VERSION **обнови timestamp `app/exportmeta.cpp`** (`(Get-Item app\exportmeta.cpp).LastWriteTime = Get-Date`) и только потом собирай: версия передаётся в код через `-D` (DEFINES), а nmake из-за смены `-D` файл не перекомпилирует — в бинаре останется старая строка. Проверка: экспорт и `export_info.json` → `exporterVersion`.
- **Релиз-zip:** `cmd /c "E:\Projects\tMC\make_release.bat"` → `E:\Builds\tMC\package\OSMC-<версия>-win64.zip`. Перед этим: тесты зелёные, секция `[Unreleased]` в `CHANGELOG.md` переименована в `[версия] — дата` (сверху новая пустая `[Unreleased]`).
- **Текст коммита** (когда попросят): на английском, первая строка в стиле `feat: ...` / `fix: ...`, дальше список пунктов. Без `Co-Authored-By`.

## 8. Типичные ловушки (уже наступали)

- `VoxelStore::set(..., IdAir)` — пустая операция. Нужен `erase()`.
- Файлы из `resources/` копируются рядом с exe при сборке: забыл пересобрать/скопировать — тестируешь старые правила.
- `osmc.exe` заблокирован запущенной копией — линковка падает с `LNK1104`.
- Переменные окружения `PROJ_LIB`/`GDAL_DATA` чужих программ ломали проекцию — программа теперь всегда берёт данные рядом с exe (`app/main.cpp`), не меняй это.
- Тесты запускают `osmc.exe --lang en`: сообщения, которые они ищут, английские. Не меняй английские тексты логов без нужды.
- Цвета декора (детсады, школы) подобраны так, чтобы не совпадать с цветами, используемыми проверками в `tests/tools/verify_mc_export.py`. Новые цвета проверь тестами.
- Скриншоты и `images/screen/` — не в Git (кроме `images/shots` и `online_*/data_*`).
- Сети нет в тестах: не добавляй в тесты обращения к интернету.
- Сборка в **чистую** shadow-папку (`TMC_BUILD` в несуществующий каталог) падает сразу на rcc: `RCC: Error in 'release\qmake_qmake_qm_files.qrc': Cannot find file '...\release\osmc_ru.qm'` — qrc от TRANSLATIONS ссылается на `.qm`, которого в пустой папке ещё нет (в обжитой `E:\Builds\tMC` он лежит с прошлых сборок). Лечение: перед `build.bat` создать `release\` и сгенерировать файл: `New-Item -ItemType Directory -Force <build>\release; lrelease translations\osmc_ru.ts -qm <build>\release\osmc_ru.qm` (lrelease — из `QTDIR\bin`).
- Синтетическая тестовая сцена из одних только лесов/парков/площадок не экспортируется: растительность и площадки не создают воксельных чанков — экспорт падает с «Could not voxelize a single object (empty or too huge meshes)». Добавь хотя бы пару зданий (например, по углам прямоугольника) — они задают и границы мира.
- В режиме `--flat` пустые чанки внутри прямоугольника данных землёй не заполняются — «пустых мест» для шага 3.51 почти не остаётся. Проверять шаговый лес/одиночные деревья надо в обычном режиме (без `--flat`): там прямоугольник данных и «дыры» в нём заполняются землёй.
- Генераторы тестовых `.osm`: перевод метров в градусы — `метры / (111320 * cos(lat))` (не `/1000`!). Признаки «сцены, сжавшейся до субблочных размеров» в логе: `Objects: N (skipped: M)` с пропущенными полигонами и `there were 1 m² of forests` в строке «Vegetation topped up».
- Замеры времени шагов: `MCX_LOG_STEPS=файл` пишет строки `[mcx] HH:MM:SS имя <ms> ms`, где `<ms>` — время с момента ПРЕДЫДУЩЕЙ строки (не накопительное). Длительность шага 3.5 — строка `before 3.51`, шага 3.51 — строка `before 3.55`.
- В пробниках по миру: мировые координаты из локальных метров сцены — `worldX = localX − centerX`, `worldZ = centerY − localY` (ось Z перевёрнута; центр — середина bbox данных).
- Региональный файл `.mca` покрывает 32×32 чанка (512×512 блоков): 16 region-файлов (4×4) — это мир до 2048³, а не «маленький». Размеры мира проверяй диапазоном чанков (`xPos/zPos` из NBT), а не числом region-файлов.
- Идентификаторы игровых регистров Minecraft (биомы, сущности, блоки) — НЕ помнить на слух, а сверять с вики minecraft.wiki / официальными чанклогами / файлами игры. Ошибка 1.2.26: биом болота записывался как `minecraft:wetland` — такого ID в игре НЕТ (болото — `minecraft:swamp`); «wetland» — только тег OSM `natural=wetland` и термин «wetland biomes» в вики (группа биомов река/болото/пляж). Быстро не выясняется — спросить владельца (правило §5.2). Игра с несуществующим ID в палитре биомов чанк либо крашит, либо (с модами) молча откатывает — цвета не красятся.
- Лес `vegpol 71111110` площадью ≥5000 м² получает `VegSite::spruce` (см. `8490`–`8500`) — лесной цикл режет его до ~38% клеток сетки («ёлки редкие») НЕЗАВИСИМО от климатической зоны, а в циклe ветка `site.spruce` стоит РАНЬШЕ `zt.jungle`. Признак в мире: «разреженный однотипный лес», а зональная ветка (свои деревья/лианы/большие деревья) не срабатывает вовсе. Порядок веток в лесном цикле: `pale` → `park` → `intra` → `spruce` → зональные.
- Если «нетstats/деревьев меньше ожидаемого» — не вери на глаз: воспроизводи сетку шага 3.5 в Python (`colHash`/`pairKey` — простые, копируются) и сверяй каждую клетку-кандидат с миром. Так за один прогон видно: доходит ли код до ветки, и где гейт режет.
- `QComboBox::setMaxVisibleItems(N)` молча игнорируется, когда для виджетов применена таблица стилей (в приложении qss): попап показывает все пункты. Рабочее лечение: подкласс QListView с переопределённым `sizeHint()` (высота = N реальных строк) через `box->setView()` (setView — до добавления пунктов!). Попап sized by sizeHint — и размер, и место открытия считаются от него.
- Стилизованный комбобокс получает styleHint `SH_ComboBox_Popup=1`: попап выравнивается по ВЫБРАННОМУ пункту — с последним выбранным список растёт ВВЕРХ. Отключать через `QProxyStyle` c `styleHint(SH_ComboBox_Popup) -> 0`, поставленный на УРОВНЕ ПРИЛОЖЕНИЯ (обернуть Fusion в theme.cpp, «свои» комбо помечать dynamic property и смотреть `w->property(...)`). Пер-виджет `box->setStyle()` НЕЛЬЗЯ — он отключает qss приложения для виджета (комбо становится нативно-серым с серым текстом). Двигать окно попапа в showEvent/eventFilter(Show) — ненадёжно (Show приходит поздно/не доходит).
- Правила стилей из qss приложения или от предка-диалога могут молча НЕ доходить до скроллбара попапа комбобокса (окно-попап — отдельное окно). Стиль скроллера задавать НА САМОМ виджете: `view->verticalScrollBar()->setStyleSheet(...)` — применится гарантированно.
- `paletteIndexOf("имя")` при отсутствии имени возвращает -1, и `IdPaletteStart + (-1)` молча совпадает с соседним enum (IdStone) — объект строится булыжником/камнем без единого предупреждения (так торговые автоматы вестибюля и `qPBlk` лаборатории вышли камнем: `minecraft:polished_blackstone` не было в палитре). Перед использованием нового имени через `blk()`/`blkName()` убеждайся, что строка есть в `kBlockPalette`, иначе допиши в конец.
- Зонды, воспроизводящие экспортные хеши (`finHash`/`v30` и т.п.) по координатам из мира: аргументы хеша — часто ЛОКАЛЬНЫЕ координаты объекта (`miny + lyF` = локальный ряд этажа, например 3), а не мировые; угадать офсет по готовому миру нельзя. Достоенный способ получить фактические корзины — временный отладочный дамп из самого экспорта (env-гейт + запись в файл), после замера удалить.
- Имена блоков в палитре зондов сверяй с реальным выводом `blockName`/палетой чанка: кашпо — это `minecraft:potted_*`, а не `flower_pot`; legacy `minecraft:stairs` в сохранённом чанке читается как `oak_stairs`.
- Скриншотные замеры на фейковом экране (`QT_QPA_PLATFORM=offscreen`) — КРАЙНИЙ случай, применять долго (проба с moc/rcc, пересобирается несколько раз): сначала живая проверка (попросить владельца открыть окно), проба — только для того, что глазом не видно: точная геометрия, направление открытия, порядок событий.
  - Фейковый экран маленький (~800×480), аргументы вида `offscreen:size=1920x1080` МОЛЧА игнорируются. Чтобы проверить «влезает/открывается вниз» — прижимать окно к верху фейкового экрана (`w->move(100,0)`) и уменьшать контент пробы (`::item { min-height: 20px }`), а не пытаться увеличить экран.
  - Шрифтов в offscreen нет: высоты строк и текстовые метрики меньше реальных, текст на grab не рисуется (видны только цветные плашки). Геометрия и направление достоверны; наличие скроллбара, тексты и сочетаемость цветов — только в живом окне.
  - Переполнение списка в пробе форсировать явно (докинуть items + `min-height`), иначе `scrollMax=0` и «скроллбар не нужен» — следствие фальшивых строк, а не кода.
  - `rcc x.qrc -o rcc_x.cpp` (Qt 5.15): ресурс регистрируется static-initializer'ом в самом сгенерированном файле; `Q_INIT_RESOURCE(имя)` не звать — функция генерируется без суффикса (LNK2019).
  - Механика: `box->showPopup(); qApp->processEvents();`, читать `cont->y()` против низа комбо, `cont->height()`, `verticalScrollBar()->maximum()/isVisible()`, цвета — `widget->grab().save(png)` (окна показывать не нужно); вывод — в файл, qWarning в консоли не виден.
- Растительность из шаблонов (палые леса: `leaf_litter`, `tall_grass`, ковры) кладётся id из `g_caveStates` (`>= IdCaveBase`), а не enum-константами — `isVegBlockId` их НЕ знала и считала «постройкой»: точечные объекты (скамейки, павильоны, скульптуры) молча пропускались целиком. Проверки «клетка свободна / это растительность» обязаны покрывать и диапазон шаблонных состояний (now: разбор имени `leaf_litter`/`*_leaves`/`*grass*` и т.п. в `isVegBlockId`); стволы (`_log`, `stem`) вырубать нельзя — они настоящие блокеры.
- Плоские многаклеточные объекты (павильон 3×3, стенд 2×2, скамья 1×2) на холмистом рельефе: уровень пола брать как МАКСИМУМ `surfaceTop()+1` по всему футпринту (не от узловой колонки), иначе соседние колонки оказываются «заняты землёй» и объект никогда не строится; низкие колонки до уровня пола добывать цоколем (тот же материал пола).
- Вложенный `switch` внутри `case` внешнего: `break` в обработке выходит только из ВНУТРЕННЕГО switch — счётчики/общий хвост кейса после внутреннего switch выполняются повторно (так пропущенная скульптура засчитывалась построенной, и placed+skipped давало N+1). Вложенные развилки в кейсах писать флагами/ранними выходами, счёт инкрементировать ровно в одной ветке.
